# ADR 0002: D-Bus IPC with zbus

- **Status:** Accepted
- **Date:** 2026-11-07

## Context

Spec §9 asks for operation progress on D-Bus so independent applications can observe it, with consistent snapshots, sequence numbers, reconnection and language independence.

## Decision

- **Library: `zbus` 6.** It's pure Rust (no libdbus), typed, and runtime-agnostic: `zbus::block_on` drives it without adopting Tokio, which would be a second event loop next to GLib.
- **Threading:** a dedicated IPC thread. Manager subscribers run under the manager's locks and only enqueue into an **unbounded** channel. That guarantees lifecycle events are never dropped and worker threads never wait on D-Bus. Progress is already throttled by the manager, which bounds the volume.
- **Contract:** typed structs, not JSON. Each signal carries the manager's sequence number, and `GetActiveOperations` returns the snapshot's sequence. Clients subscribe first, then snapshot, then apply newer events, and resync on gaps or owner changes ([protocol](../ipc/protocol.md)).
- **Identity:** a bus name separate from the GApplication id. No name replacement or queueing, so a second instance runs without publishing.
- **No D-Bus activation** while the manager lives in the UI process.

## Consequences

- The protocol is versioned (`GetProtocolVersion`), and `OperationInfo`'s signature is pinned by a unit test.
- `seshat-progress` proves that an independent client works, and its integration test runs the real binary against the real service on a private bus.
- Moving the manager to a daemon later only moves `IpcService`.
